## 0. Run discipline (read this twice; it is what makes the run count)
- Your FIRST command is `TZ=Australia/Sydney date -Iseconds`. That is START. DEADLINE = START + 48 minutes. Write `START=… DEADLINE=…` into a scratch file and re-read it before every decision to stop or skip.
- A run is judged on two numbers you must write to its meta row: `minutesUsed` and `queueRemaining`. Finishing while more than 5 minutes remain AND the queue query still returns rows is a FAILED run: then you set `lastAttemptOk: false` and `stoppedEarly: true` yourself and say so in `lastAttemptNote`. Never describe an early stop as success, never write "left for next time" while time remains.
- Work in loops: run the queue query, take the next batch, do it, write it with hq_merge at once (a crash then loses one batch at most), run `date`, compare with DEADLINE, repeat. The queue query decides what is next; you never decide a step is unnecessary because "the previous run did it".
- Chrome hiccups are normal, not reasons to stop: blank page → wait 3 s and read again (3 tries); wrong thread opened → navigate back and retry once; dialog stuck → press Escape. Chrome unreachable after 2 retries 30 s apart → go straight to the meta step with `lastAttemptOk: false` and reason "Chrome unreachable".
- Finish gate, run it BEFORE the meta row: `date`; if DEADLINE − now > 5 min and the queue query returns rows, go back to the loop. Only when the gate passes: write the meta row, close the tab you opened, give the 4-line summary.
- Writes: ONLY `select hq_merge('<table>', '<json array of {"id":..., "data":{...}}>'::jsonb);` (Supabase project `hucqdrekawzsrbbkczgj`; load with ToolSearch "select:mcp__Supabase__execute_sql"). It upserts and merges, keeping fields you do not mention. Up to 20 rows per call. Escape ' as ''. Never `update`/`delete`/`insert` (they trigger approval prompts nobody can answer).

## 3. The queues, in priority order (each is one SQL; take 10 rows, work them, merge them, `date`, repeat)
A. Manual marks to reconcile: `select id, data->>'displayName' n, data->>'threadId' tid from dm_threads where id not like 'pending-%' and data->>'threadId' is not null and ((data->>'manualReplyAt')::timestamptz > coalesce((data->>'lastVerifiedAt')::timestamptz,'2000-01-01') or (data->>'manualFollowUpAt')::timestamptz > coalesce((data->>'lastVerifiedAt')::timestamptz,'2000-01-01')) limit 10;`
B. Leads waiting on Jordan, stalest first: `select id, data->>'displayName' n, data->>'threadId' tid, data->>'lastVerifiedAt' v from dm_threads where data->>'category'='lead' and id not like 'pending-%' and data->>'threadId' is not null and coalesce(data->>'notApplicable','')<>'true' and coalesce(data->>'status','active')='active' and data->>'lastSender'='lead' and coalesce((data->>'lastVerifiedAt')::timestamptz,'2000-01-01') < now() - interval '24 hours' order by 4 nulls first limit 10;`
C. Every other lead not verified in 24 h, stalest first: same query as B without the `lastSender` condition.
D. Placeholders: the unresolved `pending-*` rows, resolved by walking the inbox list (step 4), not by search.
Rule: A until empty, then B until empty, then C in batches until 15 minutes before DEADLINE, then D (the list walk) for the last 15 minutes. If C empties early, give D the rest. The queue query decides; never skip a queue because a previous night did it.

## 4. How to process a row
- Rows with a `threadId` (A, B, C): skip it if its name is in UNREAD (merge `{"unread": true, "labelSeenAt": now}`). Otherwise navigate to `https://www.instagram.com/direct/t/<threadId>/`, wait 2 s, read the conversation (javascript_tool `document.body.innerText`, scroll up 10 ticks twice first), and merge the FULL row per the contract with `lastVerifiedAt` = now. If Instagram shows "this account can't receive your message" or the thread is gone, merge `{"lastVerifiedAt": now, "verifyNote": "<what Instagram said>"}` and move on.
- Placeholders (D): Placeholders are resolved from the inbox LIST, never from the search box (search results do not open chats). Load the unresolved names: `select id, data->>'displayName' n, data->>'tab' tab from dm_threads where id like 'pending-%' and data->>'resolvedTo' is null and coalesce(data->>'unread','false')<>'true';` Then scroll the General list (then Primary) 10 ticks at a time, reading the rows after each scroll; whenever a visible NON-bold row's name equals an unresolved placeholder's displayName, click that row, read it, write the real row (id = username, full contract) and merge the placeholder with `{"resolvedTo": "<username>", "resolvedAt": now}`. A bold row that matches stays unread: merge `{"unread": true, "labelSeenAt": now}`. When the list has scrolled past rows older than the placeholder's `labelSeenAt` minus 60 days, or the list stops adding rows after 3 scrolls, merge every still-unmatched placeholder you passed with `{"checkedAt": now, "checkCount": (stored checkCount or 0) + 1, "checkNote": "not in the inbox list back to <oldest label seen>"}`; when that makes checkCount 3 or more, also set `"unresolvable": true` (the dashboard then stops counting it as an unread chat). Ambiguous names (several inbox rows with the same display name) get `{"checkedAt": now, "checkNote": "ambiguous: <n> rows named X"}` and never become unresolvable. Never delete a placeholder.
- Opening by URL cannot see whether a thread turned unread since you built UNREAD. If the opened thread shows a "New messages" divider or a reply newer than the stored row that Jordan has not answered, that is fine: record it accurately (`lastSender: "lead"`, `waitingSince` = that message's time, `openedUnread: true`) so Jordan still sees it as waiting. Never skip writing a thread you opened.
- Every batch is written before the next one is opened.
